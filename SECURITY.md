### Что включить в отчёт

- **Описание уязвимости** – класс проблемы (RCE, SQLi, path traversal, обход auth и т.д.) и суть.
- **Шаги для воспроизведения** – максимально подробно, желательно с примерами curl или скриптами.
- **Потенциальное воздействие** – что может сделать злоумышленник.
- **Версия проекта** – тег или хеш коммита.
- **Окружение** – ОС, Docker, PostgreSQL, версия ComfyUI.
- **Предлагаемое исправление** (опционально).
- **Готовность к публичному раскрытию** и желание быть упомянутым в зале славы.

## Что мы считаем уязвимостью

### ✅ Принимается как уязвимость

- **RCE** через любой эндпоинт API.
- **Path traversal** через `/files/{name}` – чтение файлов вне `COMFY_OUTPUT_DIR`.
- **SQL-инъекции** в любых эндпоинтах.
- **Утечка чужих заданий/результатов** – например, пользователь A видит данные пользователя B.
- **Обход API-ключа** – доступ к защищённым эндпоинтам без заголовка `X-API-Key`.
- **Обход rate‑limiter** – превышение лимита `RATE_LIMIT_PER_MIN` с одного IP.
- **XSS** в OpenAPI-схеме (`/docs` или `/redoc`).
- **Обход read‑only маунта** – возможность записи в `/comfy_output` из контейнера `api`.
- **Утечка секретов** (`API_KEY`, пароль БД) в логах stdout/stderr.
- **DoS** через специально созданный workflow, вешающий ComfyUI или worker.
- **Обход CORS** – кросс‑доменный запрос с домена вне списка `ALLOWED_ORIGINS`.

### ❌ Не принимается

- Уязвимости в **зависимостях**, для которых уже есть обновление – лучше создайте обычный PR с повышением версии.
- Уязвимости в самом **ComfyUI** → [github.com/comfyanonymous/ComfyUI](https://github.com/comfyanonymous/ComfyUI)
- Уязвимости в **PostgreSQL**, **Docker**, **Python** → репортить апстрим.
- Социальная инженерия, физический доступ, Self‑XSS.
- Использование дефолтного ключа `dev-local-key-change-me` – это **документированный небезопасный дефолт** для локальной разработки.

## Процесс ответственного раскрытия

1. **Получение отчёта** – подтверждаю получение в течение 48 часов.
2. **Воспроизведение** – анализ и оценка серьёзности по [CVSS 3.1](https://www.first.org/cvss/calculator/3.1).
3. **Благодарность репортёру** – согласование деталей и даты публикации.
4. **Разработка патча** – в приватной ветке (security advisory на GitHub).
5. **Координация раскрытия** – согласование точной даты с репортёром.
6. **Релиз** – новая версия с исправлением, публикация CVE/Advisory.
7. **Упоминание** – репортёр добавляется в зал славы (с его согласия) и в release notes.

## Best practices для production‑пользователей

Если вы разворачиваете Content Factory Console в production, обязательно:

- [ ] **Никогда** не оставляйте `API_KEY=dev-local-key-change-me` — сгенерируйте уникальный ключ через `openssl rand -hex 32`.
- [ ] Используйте HTTPS перед API (реверс‑прокси nginx + Let's Encrypt, см. [`DEVELOPER.md` §10](./docs/DEVELOPER.md)).
- [ ] Регулярно обновляйте сервис: `git pull && docker compose pull && docker compose up -d --build`.
- [ ] Настройте ежедневный `pg_dump` через systemd‑таймер или cron.
- [ ] Включите проверку API-ключа (`Depends(require_api_key)`) для всех роутеров, кроме `/health`.
- [ ] Установите разумный `RATE_LIMIT_PER_MIN` – ниже, чем способна выдержать ваша БД.
- [ ] Сканируйте образы на уязвимости, например: `trivy image content-factory-console-api` (см. CI workflow).
- [ ] Ограничьте сетевой доступ: наружу должен торчать только порт `8000`, всё остальное – во внутренней сети `internal`.
- [ ] Подключите мониторинг (Prometheus + алерты на рост ошибок или аномалии).
- [ ] Ротируйте `API_KEY` минимум раз в полгода.
- [ ] При компрометации ключа (утек в лог/коммит) – меняйте его **немедленно**.
